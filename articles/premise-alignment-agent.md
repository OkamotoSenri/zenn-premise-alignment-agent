## はじめに：AI導入で増えたマネジメントコスト

コーディングAIの普及で、開発速度は劇的に向上しました。しかし私たちは「速さ」と引き換えに、別の問題を抱えることになりました。

**「間違った方向への速度」も上がってしまったのです。**

| | Before AI | After AI |
|---|---|---|
| コーディング速度 | 遅い | 劇的に向上 |
| 方向性のズレ | 小さい（上司の確認頻度も低くて済んだ） | 「間違った方向」への速度も上昇 |
| 手戻りの規模 | 小さい | 以前の数倍に拡大 |
| マネジメント | 低負荷 | 上司のマイクロマネジメントが常態化 |

AIはジュニアエンジニアの思考プロセスに3つの崩壊をもたらしています。

1. **目的の不透明化**：タスクの背景や仕様を深く理解する前に、AIに「どう書くか」を聞いてしまう
2. **AIの論理的爆発**：AIは断片的な指示に対して「論理的に正しいが、ビジネス文脈を無視した解決策」を提示する
3. **思考の外部化**：AIの回答を盲目的に信じ、仕様との整合性を自分で確認することを止めてしまう

> AIは「速さ」を与えたが、「正しさの確認コスト」は人間に残された。

この課題を解決するために作ったのが **Premise-Alignment Agent（PAA）** です。

## 対象ユーザーと解決する課題

### 対象ユーザー

AIを活用したソフトウェア開発チームにおける **マネジメント層（上司）** と **ジュニアエンジニア（部下）** を対象にしています。

### 課題

AIが「速さ」を与えた結果、**「正しさの確認コスト」が人間（上司）に集中してしまっている**状況が生まれています。

- AIにより開発速度は上がったが、「タスクと異なった実装」をするケースも増えた。ズレに気づくのが遅れるほど手戻りの規模が大きくなる
- 手戻りを防ぐため、上司が頻繁に進捗確認・修正指摘をしなければならない状況になっている
- ジュニアが仕様を深く理解する前にAIへ丸投げしてしまう。AIの回答を盲信し、自分で仕様との整合性を確認しなくなる

### ソリューション

**上司と部下の間に入り、「前提のズレ」をリアルタイムに検知・修正することで、マネジメントコストを削減しながらジュニアの自走力を育てるAIエージェント。**

- 上司がタスク依頼時に「隠れた前提条件」をPAAだけに設定する。答えを先に与えないことで、ジュニアが自分で考える余地を残す
- ジュニアが前提から外れたコード変更をすると、PAAは答えではなく「問い」を投げかける。「今の意図は、当初の目的とどう紐付いていますか？」
- 自力修正できない場合のみ、ズレの原因と誤解の内容を上司のSlackに通知する。上司は状況を把握した上で会話を始められる

## Premise-Alignment Agent の3つのコア機能

### ① インビジブル・マイルストーン

上司はタスク依頼時に、通常の指示とは別に「隠れた前提条件」をPAAだけに設定します。

| 部下への指示（見える） | 隠れたマイルストーン（PAAのみ知る） |
|---|---|
| 「退会フォームに任意アンケートを追加して。保存先は `retention_surveys` テーブル。」 | 「既存の退会処理は絶対に変更しないこと。疎結合で実装すること。」 |

**なぜ「見せない」のか？**
答えを先に与えると、ジュニアは「考える」ことをやめます。前提だけを守らせることで、実装の自由度と仕様整合性を両立させます。

### ② メタ認知的リマインド

ジュニアが前提から外れた行動（コード変更・Claudeへのプロンプト送信）を検知すると、PAAは答えではなく「問い」を投げかけます。

```
「退会ロジックを直接触っていますが、エラーで退会できなくなるリスクは？」
```

問いを投げることで自走力を育て、ジュニアが自力で修正できるよう促します。

### ③ 非同期アライメント通知

自力修正できない場合のみ、上司のSlackに通知します。

- なぜズレたのか（原因の要約）
- 今どのような前提で動いているのか（誤解の可視化）

上司は「何が起きているか」を把握した状態で会話を始められます。

## 動作シナリオ例

```
Step 1: 上司が指示＋マイルストーン設定
  → 「退会フォームにアンケート追加。保存先はretention_surveysへ」
  → 隠れた前提: 既存退会ロジックは変更禁止

Step 2: ジュニアがAIに相談 → ズレ発生
  → AIが「退会処理の中に保存ロジックを書き込むのが確実」と提案
  → ジュニアは既存コードを直接書き換え始める

Step 3: PAAが検知 → 問いかけ
  → 「退会ロジックを直接触っていますが、エラーで退会できなくなるリスクは？」
  → ジュニアが自力で気づき、疎結合設計に修正

Step 4: 結果（自走の成功）
  → 上司への通知なし
  → ジュニアが自走で正しい実装に到達
  → マネジメントコスト: ゼロ
```

### 設計の核心：ビジネスロジックをAzure Functionsに閉じ込める

PAAの最も重要な設計原則は、**AIエージェントにビジネスロジックを持たせない**ことです。

```
┌──────────────────────────────────────────────────────┐
│         AI Agent（Azure AI Foundry）                  │
│                                                      │
│  ・システムプロンプト（振る舞いの定義）                  │
│  ・Tools一覧（OpenAPI spec）                          │
│  ← ビジネスロジックは持たない                          │
└──────────────┬───────────────────────────────────────┘
               │ OpenAPI Tool呼び出し
               ▼
┌──────────────────────────────────────────────────────┐
│         Azure Functions（ビジネスロジック層）            │
│                                                      │
│  ・前提条件の取得・保存（Cosmos DB連携）                 │
│  ・Slack通知の送信                                    │
│  ・GitHub/Claude Codeイベントの受信・処理               │
└──────────────────────────────────────────────────────┘
```

この分離により：

- **責務の明確化**：AIエージェントは「何をすべきか（判断）」に専念し、「どう実行するか（処理）」はAzure Functionsが担う
- **変更コストの最小化**：ビジネスロジックの変更はAzure Functions側だけで完結し、エージェントの再デプロイが不要
- **独立したテスト・デプロイ**：FunctionsとAgentを独立したCI/CDワークフローで管理できる

### 技術スタック

| レイヤー | 技術 |
|---|---|
| エージェント基盤 | Azure AI Agent Service (`azure-ai-projects>=2.0.0b4`) |

## 実装上の工夫

### 1. エージェントSDKの選定：Conversation/Response APIの採用

Azure AI Foundryのライブラリには、旧来の Thread/Run ベースのAPIと、新しい Conversation/Response ベースのAPIが存在します。PAAでは `azure-ai-projects>=2.0.0b4` の Conversation/Response API を採用しました。

Thread/Run APIは非同期ポーリングが必要で実装が複雑になりますが、Conversation/Response APIはストリーミング応答をシンプルに扱えます。AIエージェントの振る舞いをビジネスロジックから切り離すという設計方針とも相性が良い選択です。

### 2. GitHub Actionsによるコードレビューのリアルタイム監視

ジュニアのコード変更を検知するために、`post_commit_trigger` と `pre_push_trigger` の2段階でフックを設けています。コミット単位での細かい検知と、プッシュ前の最終確認を組み合わせることで、前提からのズレをできるだけ早い段階でキャッチします。

### 3. プロンプト設計：「答えを与えない」制約

PAAのシステムプロンプトで最も工夫した点は、**エージェントが直接的な答えや修正案を提示しないよう制約をかける**ことです。

ジュニアが前提からズレた行動を取ったとき、多くのAIは「正解」を提示しがちです。しかしPAAでは「なぜその判断をしたのか」「リスクをどう評価しているか」というメタ認知を促す問いかけのみを生成するよう設計しています。これにより、ジュニアの自走力を育てながらも、致命的なズレは防ぐことができます。

## おわりに

PAAは「AIを使いながら、人間の思考力を取り戻す」ためのツールです。AIが答えを出す前に、自分の頭で前提を確認する習慣——その小さなステップが、チーム全体のマネジメントコストを下げ、ジュニアエンジニアの成長速度を上げると信じています。
