## はじめに：AI導入で増えたマネジメントコスト

コーディングAIの普及で、開発速度は劇的に向上しました。しかし私たちは「速さ」と引き換えに、別の問題を抱えることになりました。

**「間違った方向への速度」も上がってしまったのです。**

| | Before AI | After AI |
|---|---|---|
| コーディング速度 | 遅い | 劇的に向上 |
| 方向性のズレ | 小さい（上司の確認頻度も低くて済んだ） | 「間違った方向」への速度も上昇 |
| 手戻りの規模 | 小さい | 大きい |
| マネジメント | 低負荷 | 上司のマイクロマネジメントが常態化 |

AIはジュニアエンジニアの思考プロセスに3つの崩壊をもたらしています。

1. **目的の不透明化**：タスクの背景や仕様を深く理解する前に、AIに「どう書くか」を聞いてしまう
2. **AIの論理的爆発**：AIは断片的な指示に対して「論理的に正しいが、仕様の背景にある意図を無視した解決策」を提示する場合がある
3. **思考の外部化**：AIの回答を盲目的に信じ、仕様との整合性を自分で確認することを止めてしまう

> AIは「速さ」を与えたが、「正しさの確認コスト」は人間に残された。

この課題を解決するために作ったのが **Premise-Alignment Agent（PAA）** です。

## 対象ユーザーと解決する課題

### 対象ユーザー

AIを活用したソフトウェア開発チームにおける **マネジメント層（上司）** と **ジュニアエンジニア（部下）** を対象にしています。

### ソリューション

**上司と部下の間に入り、「前提のズレ」をリアルタイムに検知・修正することで、マネジメントコストを削減しながらジュニアの自走力を育てる。**

## Premise-Alignment Agent の3つのコア機能

### ① 隠れた前提条件

上司はタスク依頼時に、GitHubのIssueや機能仕様（スラッシュコマンドで部下のClaude Codeに渡す内容）とは別に、「隠れた前提条件」をPAAだけに設定します。

例えば、部下には以下のようなスラッシュコマンドを渡します：

```
/premise 
@ジュニア名
issueURL
既存の退会処理は絶対に変更しないこと。疎結合で実装すること。(前提条件)
```

| 部下への指示（見える） | 隠れた前提条件（PAAのみ知る） |
|---|---|
| 「退会フォームに任意アンケートを追加して。保存先は `retention_surveys` テーブル。」 | 「既存の退会処理は絶対に変更しないこと。疎結合で実装すること。」 |

**なぜ「見せない」のか？**
答えを先に与えると、ジュニアは「考える」ことをやめます。前提だけを守らせることで、実装の自由度と仕様整合性を両立させます。

### ② メタ認知的リマインド

ジュニアが前提からズレた行動（不要なファイルの変更・既存の仕様に対する変更）を検知すると、PAAは答えではなく「問い」を投げかけます。

```
「Issue対象外のファイルを変更しているようですが、どのような意図でやっていますか？」
```

問いを投げることで自走力を育て、ジュニアが自力で修正できるよう促します。

### ③ 非同期アライメント通知

部下に対して複数回問いかけを行っても自力で修正できず変更内容が `commit `された場合、または、修正ができていないにも関わらず変更内容が `push` された場合のみ、上司のSlackに通知します。

- なぜズレたのか（原因の要約）
- 今どのような前提で動いているのか（誤解の可視化）

上司は「何が起きているか」を把握した状態で会話を始められます。

## 動作シナリオ例

```
Step 1: 上司が指示＋前提条件設定
  → 「退会フォームにアンケート追加。保存先はretention_surveysへ」
  → 隠れた前提: 既存退会ロジックは変更禁止

Step 2: ジュニアがAIに相談 → ズレ発生
  → AIが「退会処理の中に保存ロジックを書き込むのが確実」と提案
  → ジュニアは既存コードを直接書き換え始める

Step 3: PAAが検知 → 問いかけ
  → 「Issue対象外のファイル（withdrawal_service.py）を変更しているようですが、どのような意図でやっていますか？」
  → ジュニアが自力で気づき、疎結合設計に修正

Step 4: 結果（自走の成功）
  → 上司への通知なし
  → ジュニアが自走で正しい実装に到達
  → マネジメントコスト: ゼロ
```

## システムアーキテクチャ

![システムアーキテクチャ](/images/drawio.png)

### 設計の核心：アプリケーションロジックをAzure Functionsに閉じ込める

PAAの最も重要な設計原則は、**AIエージェントにアプリケーションロジックを持たせない**ことです。

```
┌──────────────────────────────────────────────────────┐
│         AI Agent（Azure AI Foundry）                  │
│                                                      │
│  ・システムプロンプト（振る舞いの定義）                  │
│  ・Tools一覧（OpenAPI spec）                          │
│  ← アプリケーションロジックは持たない                    │
└──────────────┬───────────────────────────────────────┘
               │ OpenAPI Tool呼び出し
               ▼
┌──────────────────────────────────────────────────────┐
│         Azure Functions（アプリケーションロジック層）   │
│                                                      │
│  ・前提条件の取得・保存（Cosmos DB連携）                │
│  ・Slack通知の送信                                    │
│  ・GitHub/Claude Codeイベントの受信・処理              │
└──────────────────────────────────────────────────────┘
```

この分離により：

- **責務の明確化**：AIエージェントは「何をすべきか（判断）」に専念し、「どう実行するか（処理）」はAzure Functionsが担う
- **変更コストの最小化**：アプリケーションロジックの変更はAzure Functions側だけで完結し、エージェントの再デプロイが不要
- **独立したテスト・デプロイ**：FunctionsとAgentを独立したCI/CDワークフローで管理できる

### 技術スタック

| レイヤー | 技術 |
|---|---|
| エージェント基盤 | Azure AI Agent Service (`azure-ai-projects>=2.0.0b4`) |
| LLM | Azure OpenAI Service |
| バックエンド / API | Azure Functions (Python 3.12) |
| コード変更検知 | GitHub Actions + Azure Functions（`post_commit_trigger` / `pre_push_trigger`） |
| 通知連携 | Slack SDK |
| データストア | Azure Cosmos DB |
| 認証 | Azure Identity / DefaultAzureCredential（Managed Identity） |
| CI/CD | GitHub Actions（自動テスト・Functionsデプロイ・Agentデプロイの3ワークフロー） |

## 実装上の工夫

### 1. 三段階のコード差分検知

実装差分の検知を以下の3段階にしました。また、Claude Codeに送るプロンプトもAIエージェントに送る仕様にしています。

| タイミング | 目的 |
|---|---|
| 5分間隔の定期監視 | ステージング前の作業途中を定期的に監視 |
| コミット直後 | 確定した変更を早期検知 |
| プッシュ直後 | 未解消のズレがあれば上司に通知 |

部下の意図を正確に把握するには、実装の変更だけでなく「なぜその変更をしたのか」という意図も考慮する必要があります。その意図が最も反映されているのがClaude Codeに送るプロンプトであるため、プロンプトも検知対象に含めています。

### 2. V-netなしでAzure FunctionsからのみCosmosDBへのアクセスを許可

仮想ネットワーク（V-net）を使わず、Managed Identity + Cosmos DB のRBAC（ロールベースアクセス制御）でAzure Functionsからのみ接続を許可する構成にしています。これにより、Cosmos DBの接続文字列やパスワードをコードに持たずに済みます。
V-net構成は運用コストが高くなるため、Managed Identityによるロールベースのアクセス制御でCosmosDBへのアクセスをシンプルに制限しています。

### 3. Azure FunctionsへのアクセスをEasy Authで制限

Azure FunctionsのエンドポイントはEasy Auth（App Service 認証）で保護しています。git hooksなど外部からのHTTPリクエストに対して、Azure Functionsのエンドポイントレベルで認証を要求する構成により、アプリコードを変更せずにインフラ層で不正アクセスを防ぐことができます。
また、AIエージェントとOIDCプロバイダー（GitHub）からのリクエストのみを受け付けるよう制限しています。これにより、AIエージェントがToolを実行する場合とGitHub Actionsによるデプロイ時にのみアクセスできる構成になっています。

### 4. AIエージェントとAzure Functionsのデプロイを分離

エージェント定義とAzure Functionsを独立したCI/CDワークフローでデプロイしています。分離により以下の3つの利点があります。

- **デプロイ時間の短縮**：変更のない側のビルドが走らない
- **影響範囲の明確化**：何を変えたら何がデプロイされるかが自明
- **ロールバックの単純化**：エージェント定義だけ前バージョンに戻す、といった操作が可能

## プロンプトの工夫

### 思考フローの明示的な構造化

ステップ1〜3に分けて思考プロセスを明示し、エージェントが「まずロードマップを作る → モニタリング → 対応」という順序で動くよう制御しています。

### NG/OK例による制約の具体化

制約事項に抽象ルールだけでなく具体的なNG/OK例を示しています。「前提条件という言葉を使うな」という指示だけでは解釈がブレますが、例を示すことでモデルの出力トーンが安定します。

### エラーハンドリングの明示

HTTPステータスコードの種類別に対処方法を記述することで、ツール呼び出し失敗時の自律的な回復行動を定義しています。

### プロンプトインジェクション対策

Claude Codeのプロンプトやコード差分にはユーザーが入力した内容が含まれるため、悪意ある指示が混入するリスクがあります。意図しない命令として処理されないよう、プロンプトレベルでの対策を施しています。

## おわりに

PAAは「AIを使いながら、人間の思考力を取り戻す」ためのツールです。AIが答えを出す前に、自分の頭で前提を確認する習慣——その小さなステップが、チーム全体のマネジメントコストを下げ、ジュニアエンジニアの成長速度を上げると信じています。
